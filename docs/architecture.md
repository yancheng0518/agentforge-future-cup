# AgentForge 第一版实现说明

本文描述当前源码中的实现边界，依据《项目策划案.md》和《交接提示词.md》。功能实现、平台测试、真实模型调用和真实容器验收是不同证据，不能相互替代。

## 系统组成

React 工作台通过 `/api` 访问 FastAPI。浏览器只提交任务和 Agent 配置；模型密钥保留在后端环境变量或本地 `.env`，不通过配置 API 返回。应用以 `127.0.0.1` 绑定本机，Origin 和 Host 检查限制浏览器跨站写入。它是单机开发工具，尚未实现公网多用户认证、租户隔离或权限系统，不应直接暴露到公网。

后端 `definitions.py` 定义预置 Agent 和两个工作流模板；`engine.py` 执行任务图、调度、验证门和有限修正；`runtime.py` 提供模型适配、受控文件读写、关键词检索、差异及容器测试；`storage.py` 将配置和运行证据持久化到 `.agentforge/agentforge.sqlite3`。平台代码、`examples/todo` 目标示例、`.agentforge/runs/<id>/candidate` 候选副本与 `acceptance` 独立验收代码分离。

## 配置和规划的真实边界

Agent 可新增、启停和修改提示词、模型、能力与可用工具。角色限定为规划、开发、测试、审查、修正；能力与工具名称也由后端白名单限定。每次更新产生新版本，旧版本不覆盖。新运行复制当时的 Agent 配置和工作流定义，历史运行及恢复继续使用这些版本；修改当前 Agent 配置后，需要新建运行才能使用新版配置。

工作流采用代码化定义，并在界面中展示。两个模板共享 DAG 执行器和验证子工作流。初始任务按依赖顺序执行；验证子工作流中的测试和初步审查真实地并发调度，随后汇总审查；验收门根据工具和审查结果选择结束、修正或转人工。开发模板最多修正两轮，审查模板不写候选代码。

**规划 Agent 的任务拆分输出会进入后续 Agent 上下文，但当前不会动态改写执行 DAG。** 节点、依赖、优先级和可执行操作由受控模板决定。这是带验证与有限修正扩展的模板执行器，尚不是任意任务图编辑器，也没有拖拽编辑器、模型自主增删执行节点或任意表达式条件语言。

## 自定义调度

调度先检查节点依赖。外部依赖必须有已持久化的成功节点，未知依赖和循环依赖会明确失败。多个就绪节点按优先级降序、节点 ID 升序进入调度。

对每个任务，调度器筛选本次运行快照中已启用、具备要求能力和必需工具权限的 Agent。候选按当前执行负载升序、能力标签数量升序、Agent ID 升序排列。较少能力标签作为专用角色的平局选择依据，不代表已测量的模型质量。分配时增加负载，在调用结束、失败或取消时释放。平台 API 限制最多四个未结束后台运行。

开发和修正操作同时需要 `candidate_diff` 与 `read_project` 权限，测试需要 `run_acceptance`。模型主动调用的只读工具还由运行器再次检查白名单和参数。预填充上下文包含当前项目和检索资料；工具权限限制操作，并不构成对上下文内容的访问分级。

普通 Agent 调用失败后，最多再尝试一个其他匹配 Agent，记录排除失败 Agent 后的候选和选择原因。无匹配 Agent、模型超时和结构化输出无效分别留下明确错误。当前负载是单进程内计数，不是分布式资源调度；没有抢占、配额成本最优化或已训练的调度策略。

## 工具、知识和验证

候选修改只接受 `todo.py` 的完整文件内容。运行器检查路径白名单和大小，然后生成实际 unified diff；不会因收到 Python 源码就将它导入或在宿主机执行。审查模板没有候选写入节点。

知识库来自 `knowledge/*.md`。检索以英文词与中文字符匹配计分，返回最多三个资料片段和具体文件路径；这些片段进入 Agent 上下文，模型可以通过被授权的 `knowledge_search` 再次检索。当前是本地关键词检索，不包含向量数据库、语义 embedding、自动网页采集或长期自主学习。导入资料目前通过在该目录添加 Markdown 文件完成。

自动测试只能经 `Runtime.test` 调用受控 Docker Linux 容器。镜像或引擎缺失时结果为 `blocked`，不会转为宿主机子进程运行。容器参数限制网络、写入权限、Linux capabilities、进程、内存和 CPU；候选与独立验收文件只读挂载。可信测试驱动运行在父进程，候选只由独立 worker 子进程导入；测试通过 RPC facade 验证候选行为，候选标准输出被子进程管道捕获，不直接转发为验收输出。返回对象的修改也会回传，避免 RPC 序列化掩盖返回值应为副本的验收条件。具体测试日志、退出码、隔离标识和验收文件摘要来自测试驱动和运行器，不来自模型自述。

成功条件同时要求运行器报告测试通过、隔离成立、退出码为零，以及最终审查的 `passed` 为真。模型在输出中自行写入 `test: passed` 或伪造 `tool_calls` 字段不会改变这些证据；模型返回内容与运行器生成的工具记录分别存储。工具正常返回 `blocked` 或 `failed` 时，事件也明确标注该状态，不把“接口返回了结果”显示为验收通过。

验证开始时绑定候选内容摘要；结束前再次检查。验收过程中候选变化会阻止成功。用户点击明确确认后，应用接口重新比较已验证摘要，并由运行器检查目标基线冲突，才写入受控目标示例。应用操作串行化，防止重复请求并发覆盖。候选、模型输出和容器程序均不可自行调用应用接口。

父测试进程与候选 worker 目前仍处在同一个容器、使用同一 UID，这不是针对恶意代码的强对抗隔离边界；候选可能干扰同 UID 进程。分离进程主要防止候选直接篡改同一 Python 解释器中的 unittest 对象，以及将普通标准输出当作验收证据。容器参数的代码实现不等于安全验收完成。真实容器执行、验收结果采集和失败清理均需在可用环境中实测；不得因宿主平台单元测试通过就声称任意恶意 Python 已被可靠隔离。

## 记录、指标与恢复

SQLite 保存不可变 Agent 版本、运行配置快照、节点状态、追加事件和步骤快照。成功节点与对应的恢复上下文、快照事件在同一事务提交，避免进程在两次写入之间退出后，出现“节点成功但恢复输出丢失”。

恢复只重新执行尚未成功的节点，成功节点复用已保存结果。恢复验证前重新读取候选；如果内容摘要变化，旧验证节点失效，重新测试和审查。服务重启把遗留的运行中状态改为阻塞，并保留恢复入口。快照用于继续计算，不表示撤销文件修改、模型调用费用或其他外部操作；失败节点重试也不承诺外部请求恰好执行一次。

事件保存调度依据、Agent 结果、工具输入输出、验证意见、修正反馈、错误和节点快照。展示的是可解释的执行摘要与调度规则，不是模型内部思维链。

`model_calls` 记录运行器报告的已尝试模型 HTTP 请求次数；`model_tokens` 记录服务返回的 token 用量。失败异常携带的请求计数、已完成工具轨迹也会累加。若某个失败未提供完整计量信息，`model_metrics_complete=false`，计数只能当作已知下界；零不表示可以确定未发生计费。`agent_invocations` 另外记录 Agent 调用次数，模拟 Agent 的 provider 请求数为零。供应商账单、重试计费和费用估算没有被这些指标替代。

## 已验证范围与未完成工作

`tests/test_engine.py` 和 `tests/test_api.py` 使用明确标记的 `StubRuntime`，验证顺序、并行、条件与有限修正、调度负载、失败重新分派、工具权限、恢复与内容失效、配置版本、应用确认与冲突、模型错误计量及不可伪造运行器结果等平台行为。这些测试不执行候选 Python，不访问真实模型，也不证明 Docker 可用。`tests/test_runtime.py` 使用伪模型与容器传输验证接口边界，证据性质相同。

当前完整闭环仍取决于本地模型配置和可用 Docker Linux 环境。对真实模型返回格式、工具调用兼容性、额度、限流、价格，以及真实容器中的验收失败、修正后通过，须分别留下实际运行记录。模拟模式首轮候选的筛选缺陷是预设演示故障，必须持续标注。

3–5 个独立开发任务、单 Agent 与固定串行多 Agent 的对照实验、同等模型/预算条件下的收益结论尚未完成。现有调度策略是可解释的自定义实现，不能据此宣称优于基线。公网部署、新机器完整复现、正式无障碍审计及比赛材料仍需要独立验收。
