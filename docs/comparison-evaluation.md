# 同模型、同任务、同预算上限的同期对照

本次比较使用新建运行，不把此前 4/4 真实开发或三项预设缺陷修正的成绩当作同期对照。历史数据保持原样。全部任务、策略、顺序、预算、代码和停止规则在第一次模型请求前冻结；失败不补跑、不替换、不从分母排除。

## 比较什么

- `single_direct`：一个固定开发 Agent 直接实现需求；可信运行器执行独立 Docker 验收。失败时把真实结果交回同一个 Agent，最多修正两轮。没有额外规划、测试解读或独立审查 Agent。
- `fixed_serial`：与并行组完全相同的五类 Agent 配置，固定节点到 Agent 的映射，按规划、开发、静态检查、测试、汇总审查的顺序执行；失败时调用固定 fixer。没有动态重新分派。
- `dynamic_parallel`：使用平台的能力/权限/负载调度及测试和静态检查并行机制；失败时最多两轮修正。

串行与并行组在静态检查时都看不到当前测试或最终审查，测试解读时都看不到当前静态/最终审查；汇总审查才能看到两者。这样避免“并行尚未返回、串行已经返回”的上下文差异。固定串行先静态检查再测试，事件和步骤真实串行执行。

共同输入是四项已固定任务的需求、基线、知识资料、允许工具和独立验收。角色提示词和中间上下文属于策略差异，完整冻结；不声称各组发送完全相同的请求字节。

## 预算与样本

默认四项任务 `completion`、`bulk_edit`、`priority_query`、`json_merge`，各策略各重复两次，共 24 次试验。每个任务/重复构成一个三组配对块；第一遍轮换组别位置，第二遍反转对应顺序。批次内每次仅运行一个试验，模型请求的最小开始间隔统一为 4.2 秒。

每次试验具有相同上限：

- 最多 24 个真实 HTTP 请求，包括格式重试和失败请求；并发请求先原子占用额度，拒绝发送的请求另记为 budget denial，不计真实调用。
- 每请求最多 4096 个输出 tokens、180000 字节 JSON 请求正文；按实际发送的 UTF-8 序列化方式计算正文大小。
- 每个 Agent 调用最多 4 请求，最多 1 次格式重试；前两次允许只读工具，重试禁止工具。
- 最多 2 轮代码修正，单次试验 600 秒。

这是相同资源上限，不是相同实际消耗。各组可能提前完成或失败，不能为了凑齐调用数人为重复。输入 tokens、实际输出 tokens 和服务费用不被称作等额；记录服务 usage 与计量完整性，不推算账单。取消或超时后未知的用量保持未知。

## 统一评价标准

主要终点是**最终未改变的真实模型候选，通过同一套完整的 10 项独立 Docker 验收**。必须关联候选生成、落盘、候选哈希、冻结验收哈希、实际测试与最后候选，不能只看服务状态或模型声称“通过”。

各策略原生流程是否完成单独报告。多 Agent 的最终 gate 还要求有效的模型审查；单 Agent 没有独立模型审查，不能填造 `review.passed=true`。例如代码已经通过 Docker、但多 Agent 的最终 JSON 审查失败时，功能终点可通过而原生流程仍失败，两项事实同时保留。

自然代码失败只计真实候选在完整独立测试中失败。协议格式错误、HTTP/预算/容器故障分别归类；格式重试不计代码修正。自然修正还须有失败测试、反馈、同轮后的真实代码修改、哈希变化与复验链。维护者基线缺少功能不算自然失败。本批三组均无缺陷注入；正反控制中的合成缺陷仍单列，不计入模型成绩。

## 复现

先按 README 准备依赖、本地模型配置和 Docker。候选仅在受控容器执行。对照脚本直接使用隔离数据库和运行器，无须启动前端/API，也不改主运行历史。

```powershell
.\.venv\Scripts\python.exe scripts\preflight.py
.\.venv\Scripts\python.exe scripts\probe_task_suites.py
```

使用该次输出的控制证据路径，先检查冻结计划；输出目录必须不存在：

```powershell
.\.venv\Scripts\python.exe scripts\evaluate_comparison.py --controls .agentforge\task-controls\20261108T092717Z-4b7676\evidence.json --dry-run --output .agentforge\comparisons\review-plan
```

正式运行另建目录，真实请求可能计费：

```powershell
.\.venv\Scripts\python.exe scripts\evaluate_comparison.py --controls .agentforge\task-controls\20261108T092717Z-4b7676\evidence.json --repetitions 2 --max-requests 24 --timeout 600 --output .agentforge\comparisons\reproduce-three-arm
```

控制证据会复核原始结果、任务与运行器哈希和镜像；本批测试运行使用解析后的不可变本地镜像 ID。镜像 ID 可保证这台机器上的同一镜像，不是可从远程拉取的发布 digest；换机仍需按安装说明构建并重新做控制。

`preregistration.json` 不可修改；`state.json` 保留所有计划试次，`summary.json` 汇总，`trials/*/evidence.json` 包含原始事件、候选、快照、计量与分类。请求正文和安全响应另存于 `requests/`，不包含 Authorization、真实密钥或模型思维链。出现冻结条件变化、超时或未结束的请求时停止后续提交，未提交试次保留。没有自动重启或选择性重测；要改变代码或条件应另建批次。

## 本地记录故障与单独续采

原批次 `20261108T093911Z-d4cafa49` 在第 15 次试验期间因 Windows `WinError 5` 无法将 `state.json.pending` 原子替换为 `state.json`，停止后续提交。最终错误记录已保存。不能据此确定哪个进程占用了文件。第 15 次已有 3 次成功模型请求和真实候选，但容器验收被中断，没有完整 10 项结果；它是本地观察程序中断，不是自然候选代码失败。原导出将其 `state` 写为 `complete`，但 `native_status=blocked`；复核应以原事件、未完成验收及批次错误同时判断，不能把这个生命周期字段当成通过。

原预注册、状态、候选和失败全部保留，不改写原批次。修复仅给相同 `.pending` 文件的原子替换增加有限重试：最多 6 次、累计等待 1.55 秒；不会重新生成内容、调用模型或重跑测试，其他异常立即抛出，重试耗尽仍停止。后续观察异常也标记为 `interrupted`。

新 `--continue-unsubmitted` 是**单独预注册的追加采集阶段**，不是恢复或重测旧运行。它绑定原预注册和状态 SHA，只选择原计划尚未提交、无 run ID 的 16–24 号试次；保留任务、重复号、块号、组内顺序和原试次编号。已提交的成功、HTTP 失败及第 15 次中断不重跑。模型、任务、角色/工作流、预算、镜像及推理运行代码必须与原批一致；差异只允许观察器写入、续采和合并报告脚本，并逐文件记录前后 SHA。永久独占 claim 防止同一父批次重复续采；不清除不确定提交的 claim 来重跑。

```powershell
.\.venv\Scripts\python.exe scripts\evaluate_comparison.py --controls .agentforge\task-controls\20261108T092717Z-4b7676\evidence.json --continue-unsubmitted .agentforge\comparisons\20261108T093911Z-d4cafa49 --repetitions 2 --max-requests 24 --timeout 600 --output .agentforge\comparisons\continuation-review --dry-run
```

检查新计划后，去掉 `--dry-run` 并换成不存在的新目录才能提交。已执行过的父批次存在 claim 时会拒绝重复计费；从零复现实验应使用上面的全新 24 次命令。联合报告维持原 24 个槽位，每个最多一次真实提交，并单列阶段与基础设施中断。采集中断带来时间间隔，因此不能描述成一次无中断的同期实验。

实际追加阶段为 `20261108T100258Z-dd103ac6`，其 `continuation` 字段记录父哈希、保留/选择的编号及四个观察脚本的差异；`continuation-claim.json` 保存领取记录副本。旧阶段的审计结果保持 partial，不能把它修改为 completed。两个阶段结束后，以下命令只读核验并生成新的联合报告，不发模型请求、不执行候选：

```powershell
.\.venv\Scripts\python.exe scripts\merge_comparison.py --parent .agentforge\comparisons\20261108T093911Z-d4cafa49 --child .agentforge\comparisons\20261108T100258Z-dd103ac6
```

合并器复核全部请求正文/归档与候选哈希，重新计算并核对原分类，验证组别、任务、预算、父引用、源码差异和每个运行 ID 的唯一性。输出为子阶段 `combined-summary.json`，已有文件拒绝覆盖。要复查已存在的联合报告，可使用包内的独立审计器，或在复现副本中重建报告；不要删除原始记录后重新调用模型。

## 结果与限制

已完成原 24 个计划槽位的单次提交与证据核验：原阶段保留 15 次，追加阶段仅提交此前未提交的 9 次，没有替换任何失败。两个阶段使用真实 `deepseek-v4.1-flash`、同一平台地址与参数、同一任务快照和镜像 ID；预算为上述同一上限。联合结果在 `.agentforge/comparisons/20261108T100258Z-dd103ac6/combined-summary.json`。

- **单 Agent：功能验收 6/8，完整策略流程 6/8。** 26 次请求，已知 123,722 tokens，3 次格式重试。两次未达功能终点分别是第 8 次 HTTP 429 和第 15 次本地记录程序中断。
- **固定串行：功能验收 6/8，完整策略流程 6/8。** 66 次请求，已知 451,848 tokens，5 次格式重试。第 18、19 次在候选生成前遇到 HTTP 429。
- **动态并行：功能验收 8/8，完整策略流程 7/8。** 82 次请求，已知 575,052 tokens，5 次格式重试。第 7 次真实候选已经通过完整 Docker 验收，随后模型节点 HTTP 429，故功能成功与流程失败同时成立。

合计 **174 次真实请求、已知 1,150,622 tokens、20 次候选各通过 10/10 Docker 测试、19 次完整流程完成**。4 次 HTTP 429 没有 usage，所有组的完整用量均未知；上述 tokens 只能作为已知下界，不能据此推算准确成本。第 19 次 `model_tokens_known=0` 仅表示没有获得任何 usage，不等于免费或已确认耗用 0。

原阶段 2026-11-08 17:39:18–17:49:39、追加阶段 18:02:59–18:07:50（北京时间）。所有终止记录的运行耗时中位数：单 Agent 21.08 秒、串行 50.75 秒、并行 49.37 秒；这些中位数**包含早期 HTTP 失败和中断**，只描述观察到的耗时，不能作为成功任务速度或并行加速比。详细逐试次耗时和到达首个通过测试的时间保存在联合 JSON。

分类结果保持独立：

- 自然候选代码失败 **0**；自然失败后修正成功 **0**；审查拒绝后代码修正 **0**。本次未获得自然自修正样本。
- JSON 格式错误响应 **13**、相应格式重试 **13**；最终未解决的协议格式失败 **0**。它们不是 13 次代码修复。
- 服务 HTTP 429 **4**（第 7、8、18、19 次）；本地记录程序中断 **1**（第 15 次，按批次错误与阻断事件推断归因）；预算拒绝 **0**。
- 本次真实开发候选无预设缺陷注入。8 个正反控制、历史三项预设缺陷修正和 mock 结果均未计入这 24 次。之前的[多任务与预设缺陷实验](multi-task-evaluation.md)仍单独保留。

合并器逐份重分类并核对 **24 份试次证据、174 份请求归档、21 份候选归档**（包含第 15 次未完成验收的候选）。所有目标基线未变，所有运行 `applied=false`。额外独立审计器检查冻结源、请求正文、计量、角色和执行顺序；记录在追加阶段 `audits/`。固定串行是真正先检查后测试；并行组存在节点时间重叠，但这不是同时 HTTP 或实际加速的证明。

平台回归 **287 passed、133 subtests passed（48.71 秒）**，均不调用真实模型；其中一项用真实 Windows 文件句柄阻止删除共享，释放后验证原子写入重试恢复。其余异常注入单元测试只验证运行器的边界，不混入真实实验。完整验证记录见 `docs/verification-comparison-20261108.json`。

小样本结果仅作描述，不预设多 Agent 更好。当前专用角色通常只有一名合适 Agent，难以证明负载分配策略本身的优势；共同的请求限流会压缩并行耗时收益。功能任务同属 TodoStore，不能推广为通用软件工程效果。

本批已出现真实 HTTP 429，保留为服务错误，不计自然代码失败或 JSON 格式失败。429 的具体原因不能仅凭状态码判定为请求次数限流、token 限流或额度不足；相同客户端请求间隔无法排除平台服务波动。失败请求没有 usage 时，用量只是已知下界，不能把未知用量填成已确认的 0。时间轮换能减少位置偏差，不能消除短时间服务状态对相邻试次的影响。
